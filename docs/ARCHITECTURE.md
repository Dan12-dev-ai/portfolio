## Design Goals

The architecture optimises for four properties, in priority order.

1. **Navigation can never drift.** Every route, regardless of how it is rendered, must show the same header, footer and controls.
2. **Content is stated once.** A headline, link or statistic must be editable in one place and correct everywhere.
3. **No infrastructure to operate.** No database, no CMS, no external services beyond the runtime host.
4. **The site is its own API.** Any consumer should be able to read structured data instead of scraping HTML.

## Rendering Model

The application deliberately mixes two rendering strategies inside one Next.js App Router application.

| Strategy | Routes | Mechanism |
| --- | --- | --- |
| Static document served by a route handler | `/`, `/contact` | `readPage()` reads an HTML file from `src/`, `withChrome()` injects the frame |
| App Router Server Component | `/experience`, `/resume`, `/admin` | React components render the page and embed the same chrome string |

Both paths converge on `src/lib/chrome.ts`. This is the load-bearing decision in the codebase: because the static documents and the React pages consume one chrome implementation, the hybrid never becomes visible to a visitor.

### Why not render everything as React?

The landing and contact pages are dense, visually specific documents. Authoring them as React would require either a large component tree or a constant stream of inline styles, either of which makes the markup harder to tune. Serving a document and injecting the frame keeps the visual work in one readable file.

### Why not render everything as static documents?

The experience, resume and admin pages are genuinely structured. The resume reads from the same typed data as the API; modelling it as a string template would mean re-implementing the data binding and losing type safety. Server Components are the correct tool there.

## Static Documents

`src/landing.html` and `src/contact.html` are complete, standalone HTML documents. Each carries its own content, layout and page-level styles.

They are served by `src/app/route.ts` and `src/app/contact/route.ts`:

```ts
export async function GET() {
  return servePage({
    file: 'landing.html',
    fallback: FALLBACK_HTML,
    active: 'home',
    variant: 'light',
    offsetBody: true,
    path: '/',
    title: `${profile.name} — ${profile.role}`,
    description: profile.headline,
  })
}
```

`servePage()` performs four steps:

1. **Read** the document from disk via `readPage()`.
2. **Cache** it when `NODE_ENV === 'production'`; re-read every request in development so edits appear without a restart.
3. **Inject** the chrome with `withChrome()`, which places the header before the body content and the footer after it, and rewrites `<title>`, meta description, canonical URL and Open Graph tags.
4. **Respond** with `Cache-Control: no-store`, because chrome options can change the rendered output.

If the file cannot be read, `readPage()` returns the supplied fallback. A missing document degrades the page rather than failing the route with a 500.

### Cache invalidation

The in-memory cache is keyed by file path and never expires. Because the document files are baked into the deployment artefact and never written at runtime, this is safe. Editing a document in development is picked up automatically because caching is disabled outside production.

## Shared Chrome

`src/lib/chrome.ts` builds the site frame as strings.

| Export | Kind | Purpose |
| --- | --- | --- |
| `buildHeader()` | Function | Header markup |
| `buildFooter()` | Function | Footer markup |
| `RUNTIME_MARKUP` | Constant | Drawer, scrim, progress bar, to-top button, toast host |
| `withChrome()` | Function | Frame injection and metadata rewrite |
| `ChromeOptions` | Type | `active`, `variant`, `offsetBody` |
| `ChromeVariant` | Type | Currently `'light'` only |

The module inlines its SVG icons as string constants. This avoids an icon dependency and keeps the frame to a single synchronous call with no async resolution.

### Injection strategy

React pages embed the chrome with `dangerouslySetInnerHTML`. This is safe because the input is generated by `buildHeader()` and `buildFooter()` rather than by user input, and every interpolated value passes through `escapeHtml()` first. The alternative, converting the chrome to React elements, would mean maintaining two implementations of the same frame, which directly contradicts the first design goal.

### Fixed header compensation

The header is `position: fixed`, so it occupies no layout space. Any page whose own body has no top padding would have its first section obscured.

The `offsetBody` option solves this. When set, the body receives a class that applies `padding-top: var(--pd-header-h)`. The landing page sets it because its header is sticky rather than fixed. App Router pages handle the same compensation in their own stylesheet, using the same custom property so the offset always matches the rendered header height at any breakpoint.

## Client Runtime

`public/portfolio.js` is a single IIFE loaded by every route. It owns all interactive behaviour.

### Delegation as a correctness requirement

The runtime binds listeners to `document` and resolves target nodes through live queries at interaction time:

```js
function drawerNode() {
  return document.querySelector('[data-pd-drawer]')
}
```

It does not capture element references during initialisation. This is not a stylistic preference. The App Router can unmount and remount a page's DOM without reloading the document, and a captured reference would point at a detached node, silently breaking the feature. Because the runtime never assumes a node it captured still exists, it survives client navigation and remounting.

An initialisation guard on `window.__pdInit` prevents double-binding.

### Responsibilities

| Feature | Mechanism |
| --- | --- |
| Mobile drawer | Open/close, scrim, scroll lock, `Escape` to dismiss |
| Scroll progress | Position bar derived from document scroll |
| Back to top | Visibility threshold, smooth scroll to origin |
| Anchor scrolling | Header-aware offset so headings are not hidden |
| Status pill | Fetches `/api/health` and renders live copy |
| Copy helpers | Clipboard write with toast confirmation |
| Click beacons | `navigator.sendBeacon` to `/api/click` on outbound links |
| Reveal animation | `IntersectionObserver`, respecting `prefers-reduced-motion` |

## Content Model

`src/lib/site.ts` is the only place content is declared.

Every exported collection is typed, and the types are exported alongside the data so consumers cannot drift:

| Export | Type | Consumed by |
| --- | --- | --- |
| `profile` | `Profile` | Pages, `/api/profile`, `/api/health` |
| `socials` | `SocialLink[]` | Chrome, pages, API, connect gateway |
| `nav` | `NavItem[]` | Chrome, drawer, `/api/profile` |
| `stats`, `services`, `skills` | Typed arrays | Landing page, `/api/profile` |
| `projects`, `experience`, `timeline` | Typed arrays | Experience page, resume, API |
| `publicRoutes` | Route table | `sitemap.ts`, `/api/health` |

### Environment overrides and derived handles

External URLs resolve through `readEnv()`, which falls back to a compiled-in default. Display handles are then **derived from the resolved URL** rather than declared separately:

```ts
function handleFromUrl(url: string, fallback: string): string
```

This makes a contradiction between a shown handle and its link structurally impossible. Overriding `GITHUB_URL` in the environment changes both at once.

### Private channels

Channels marked `private: true`, currently Telegram, never expose their handle. The card renders a call to action instead and the destination is withheld from the client, keeping the server-side redirect authoritative.

## Persistence

`src/lib/store.ts` implements a JSON-file store with three collections: `messages`, `subscribers`, `clicks`.

### Write path

```text
mutate(callback)
   │
   ├─ acquire per-file lock      ← serialises read-modify-write
   ├─ read + parse JSON          ← failures yield an empty database
   ├─ callback(db) → { data, result }
   ├─ write to temp file         ← `${target}.${pid}.${timestamp}.tmp`
   ├─ rename temp → target       ← atomic on POSIX
   └─ release lock, return result
```

Atomicity comes from the rename: a reader observes either the complete previous file or the complete new one, never a partial write.

### Directory resolution

`dataDir()` returns the first writable directory among `PORTFOLIO_DATA_DIR`, `./data`, and the OS temp directory, resolving once per process. On a host with an ephemeral or read-only filesystem the store degrades to the temp directory instead of throwing, and the resolved path is exposed by `/api/health` so the degradation is observable rather than silent.

### Bounds

The click log is truncated to the most recent 2000 entries. Messages and subscribers are unbounded, because their volume is governed by real inbound traffic rather than automated events.

### Concurrency limits

The lock map is per-process. This makes the store correct for a single Node process and **incorrect across multiple instances**, where each would hold a divergent copy and overwrite the others. Scaling horizontally requires replacing this module with a shared datastore; the interface is small enough that this is a contained change.

## Request Lifecycle

### Public page, static document

```text
GET /
  └─ src/app/route.ts
       └─ servePage()
            ├─ readPage('landing.html')        cached in production
            ├─ withChrome(html, options)
            │    ├─ escapeHtml() on interpolated values
            │    ├─ buildHeader() / buildFooter() / RUNTIME_MARKUP
            │    └─ rewrite title, description, canonical, OG
            └─ Response(html, Cache-Control: no-store)
```

### Contact submission

```text
POST /api/contact
  ├─ clientKey(request)                 x-forwarded-for / x-real-ip / cf-connecting-ip
  ├─ rateLimit(key, limit, window)      429 with Retry-After when exceeded
  ├─ readJson(request)                  400 on malformed body
  ├─ validateContactPayload()
  │    ├─ sanitise + length-cap every field
  │    ├─ honeypot check                400 when `company` is filled
  │    ├─ completion-time check         400 when elapsedMs < 1200
  │    └─ field validation              422 with per-field messages
  ├─ saveMessage()                      serialised atomic write
  └─ 201 with reference code
```

### Outbound platform click

```text
GET /api/connect/github
  ├─ getSocial(platform)                404 when unknown
  ├─ recordClick()                      best effort
  └─ 302 to destination
```

The redirect is a plain 302, so the gateway works with JavaScript disabled.

## Design Decisions

### A file store instead of a database

Chosen to keep the project runnable with `npm install && npm run dev` and deployable to any Node host. The trade-off is explicit: single instance only, and no concurrent multi-writer support.

### A shared token instead of user accounts

The console serves one operator. Sessions, password resets and account recovery would add surface without adding capability. The cost is that the token is a single shared secret with no per-user revocation, and its default value is public, which is why the deployment checklist insists it be changed.

### In-memory rate limiting

Sufficient for the actual threat, which is accidental double submission and casual form spam. It is not a security control and is documented as such.

### Hand-written chrome runtime

No drawer library, no animation library, no icon package. The chrome is roughly a thousand lines of CSS and JavaScript that would otherwise pull in several dependencies for behaviour that is mostly state toggling and CSS transitions.

## Extension Points

| Goal | Where to change |
| --- | --- |
| Add or edit content | `src/lib/site.ts` |
| Add a route | New `page.tsx` or `route.ts`, then add the path to `publicRoutes` |
| Change navigation | `nav` in `src/lib/site.ts`; the chrome and drawer both read it |
| Change the frame | `buildHeader()` / `buildFooter()` in `src/lib/chrome.ts` |
| Change chrome behaviour | `public/portfolio.js`, binding through delegated listeners |
| Restyle the frame | `public/portfolio.css`, which owns `--pd-*` tokens |
| Replace persistence | `src/lib/store.ts`, behind its exported function interface |
| Add API validation | `src/lib/validate.ts` |
